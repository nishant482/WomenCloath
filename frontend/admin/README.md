# RAJO Studio

Open `/admin/` with the frontend and backend running. Sign in using the configured administrator account. For initial setup or an administrator credential change, set `ADMIN_SETUP_EMAIL` and `ADMIN_SETUP_PASSWORD` in the shell and run `node backend/scripts/set-admin.mjs` from the project root. Clear these variables afterwards. The script hashes the password, revokes that account's existing sessions, and updates `ADMIN_EMAIL` in the ignored backend environment file; credentials are never embedded in the frontend. Restart the backend after changing its environment configuration. Email signup and verification are also available using `ADMIN_EMAIL`.

The studio connects to protected `/api/admin/*` routes for products/inventory, orders/returns, users/roles, review moderation, banners, family photos, blogs, coupons, enquiries and store/shipping settings. `main.jsx` is the entry; `styles.css` contains responsive styles.

Images are optional. HTTPS/local URLs work immediately. File uploads prefer Cloudflare R2 when configured, followed by Cloudinary, Cloudflare Images or Vercel Blob. Incomplete provider credentials disable uploads rather than silently uploading elsewhere. Admin-created reviews are labelled demo reviews. COD collection/refund controls record manually completed actions; they do not transfer money.

For Cloudflare R2, activate R2 in Storage & databases, create a Standard bucket named `rajo-images`, and create bucket-scoped Object Read & Write S3 credentials. Configure server-only `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` and `R2_PUBLIC_URL`. The last value is the bucket's public HTTPS delivery base, not its S3 endpoint. R2's public development URL is rate limited and intended for testing; use a Cloudflare-managed custom domain for production delivery. Configure that separately before production activation. Uploads use unique object keys and long-lived caching; only the existing authenticated admin upload route can write. The R2 Standard free allowance is usage-based, with overage billing; activation requires Cloudflare's subscription checkout. Existing image URLs are not migrated automatically. Redeploy and verify an admin upload plus public image retrieval before considering setup complete.

The alternative Worker gateway in `backend/cloudflare-images` binds the existing private `rajo` bucket. Deploy it with Wrangler, configure its `UPLOAD_TOKEN` secret, and set the matching backend `R2_GATEWAY_TOKEN` plus `R2_GATEWAY_URL`. This gateway takes priority over direct storage credentials. It exposes public GET/HEAD only for image object paths and requires the server token for PUT; listing and deletion are unavailable. Files are limited to 3 MB and JPEG/PNG/WebP signatures are checked on both servers. Browser responses use immutable caching. Workers Free request limits also apply; no paid Workers upgrade is required by this code. Existing product images are not migrated automatically.

For Cloudinary's free plan, create an account and copy Cloud name, API key and API secret from the console API Keys settings. Set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET` in the backend environment / Vercel production environment, then redeploy. Keep the API secret server-only. Uploads are signed by the backend; no unsigned upload preset is needed. New uploads use unique IDs under `rajo/` and existing media URLs remain unchanged. Free capacity is usage-based (storage, transformations and delivery bandwidth share credits), not a guaranteed unlimited allowance for 1,000 files. Verify a real admin upload and its returned URL after configuring credentials.

For Cloudflare, enable Images in the account and create an API token scoped to that account with Cloudflare Images Edit (Images Write) permission. Set `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_IMAGES_API_TOKEN` only in the backend environment / Vercel project environment, then redeploy. Never put the token in frontend variables or Git. Configure a publicly accessible predefined variant named `public`, with scale-down fitting so product and banner photos are not cropped. Existing images are unchanged; new uploads from products, banners, family and blogs use Cloudflare delivery URLs. No domain or nameserver migration is needed. JPEG, PNG and WebP files up to 3 MB are accepted through the authenticated admin route. A live upload must be verified after credentials are configured. Alternatively, `BLOB_READ_WRITE_TOKEN` enables Vercel Blob when neither Cloudflare variable is set.

Customer signup currently works without verification email (`REQUIRE_EMAIL_VERIFICATION=false`): it creates a customer account and signs them in immediately. Existing unverified customers can sign in with their original password. Public signup never grants administrator access. Password recovery still requires configured email delivery. Set `REQUIRE_EMAIL_VERIFICATION=true` only when verification emails are configured and required again.

Customer signup requires a unique Indian mobile number and password. The storefront defaults to mobile/password sign-in; email login remains available for legacy accounts with no saved mobile number. A sparse unique `loginPhone` index protects new account identifiers without breaking legacy records. Email remains available for password recovery. Guest checkout accepts shipping details and server-validated product lines without an account; COD availability, stock transactions and idempotency are enforced for guests and signed-in shoppers. Product-card Shop Now opens a single-product checkout and prompts for garment size where required. Guest orders appear in the same admin order list and are not attached to an account solely by matching an unverified phone number.

The Blog posts navigation tab is hidden. Image library lists uploaded and migrated R2 images, supports naming, upload and reuse from product/banner/family editors. Storefront photo references were migrated using `src/media-manifest.json`; local originals remain as backups. Dashboard donut charts show actual order status, catalogue categories and inventory categories, including empty states.

The classic white/logo-red admin workspace includes Overview, Reports, Products, Inventory, Categories, Orders, Returns, Payments, Users, Reviews, Banners, Family, Blog posts, Discount codes, Enquiries and Store settings. Reports use actual paid order totals and order counts for the last 7 or 30 days in India time. Categories summarise the three supported catalogue categories; they are not a free-form category editor.

Customer carts and Customer wishlists list signed-in customers with saved items. The View action shows product names, images, quantities, sizes, current prices and availability. Guest carts remain local until customer login. Administrator sessions use a separate cookie from customer sessions, so logging into the admin panel does not sign the administrator into the public shopping account.

Record tables support search, status filters, sorting, CSV export and 10 records per page within the API's existing list limits (1,000 products; 500 for most other resources). View opens product information or order/customer details. Product and user deletion removes the record from admin lists and public access using a deleted status; historical order data remains intact. User deletion revokes sessions. The current administrator and configured owner cannot be deleted. Content, coupon and review deletion uses the existing delete endpoints. Payments and refunds record externally completed actions.
